うまくいった結果だけでなく、「なぜ止まったか」「どう切り分けたか」を残すのが目的。

- 作業は AI コーディングエージェント（Claude Code）と進めており、調査と対処の手順をそのまま記録している。
- 時刻は日本時間（JST）。
- 証跡のコマンド出力は、実際の出力から関係する行を抜き出したもの。アカウント ID やユーザー名などは載せていない。

## 詳細

### 1. 作業フォルダが、別プロジェクトの Git リポジトリの中にあった

- **事象**: 新しく作ったフォルダで `git status` を実行すると、別プロジェクトのブランチ名と、無関係なフォルダの一覧が表示された。
- **調査**: `git rev-parse --show-toplevel` が親フォルダを返した。親フォルダ自体が Git リポジトリで、このフォルダは「未追跡のフォルダ」として見えていた。
- **影響**: そのままコミットすると、別プロジェクトのリポジトリに混ざるところだった。
- **対処**: このフォルダで `git init -b main` を実行し、独立したリポジトリにした。親のリポジトリには触れていない。
- **学び**: 新しいフォルダでも、最初に `git rev-parse --show-toplevel` でリポジトリの境界を確認する。

### 2. `wsl --install` と再起動のあと、Ubuntu が入っていなかった

- **事象**: 管理者権限で `wsl --install -d Ubuntu` を実行して再起動したあと、`wsl -l -v` が「インストールされているディストリビューションはありません」と返した。
- **調査**:

  ```
  > wsl --version
  WSL バージョン: 3.0.5.0
  カーネル バージョン: 6.18.58.1-1
  > wsl --status
  既定のバージョン: 2
  ```

  WSL 本体は入っていて、既定も WSL2 になっていた。Ubuntu のアプリパッケージと、レジストリのディストリビューション登録はどちらもなかった。
- **原因（推定）**: 最初の実行では、WSL 本体（仮想化機能）の有効化と再起動の要求までで止まり、ディストリビューションの取得は行われなかった。再起動後に自動で続きが実行されることもなかった。原因そのものは確認できていない。
- **対処**: 再起動後に、通常の権限の PowerShell でもう一度 `wsl --install -d Ubuntu` を実行した。Ubuntu 26.04.1 LTS が入った。
- **学び**: 「入れた」という報告だけで先に進まず、`wsl -l -v` で状態を確認してから次の手順に進む。README の手順には「再起動後に `wsl -l -v` で確認し、Ubuntu がなければもう一度実行する」と書く。

### 3. PowerShell から WSL に渡したコマンドが構文エラーになった

- **事象**: PowerShell から `wsl -e bash -lc '...'` の形で、`for` と `if` を含む複数行相当のコマンドを渡すと、次のエラーになった。

  ```
  =: -c: line 2: syntax error: unexpected end of file from `if' command on line 1
  ```

- **原因**: PowerShell の引用符・`$` の扱いと、bash の引用符の扱いが重なり、bash に届いた時点でスクリプトが途中で切れていた。
- **対処**: コマンドをシェルスクリプトのファイルにして、`wsl -e bash /mnt/c/.../script.sh` で実行する形に変えた。以降の WSL での操作はすべてこの形にしている。
- **学び**: シェルをまたぐときは、インラインのコマンドを作り込まずにファイルにする。実行した内容がそのまま残るので、証跡にもなる。

### 4. `apt-get update` が10分以上終わらなかった

このプロジェクトでいちばん時間を使ったつまずき。

- **事象**: WSL の Ubuntu で `apt-get update -qq` を実行すると、10分たっても終わらなかった。
- **影響**: `unzip`・`pipx`・`python3-venv` が入らず、その後のツール導入がすべて止まった。

**調査の流れ**

1. プロセスとロックを確認した。`apt-get` は動いていて、ロックの取り合いではなかった。

   ```
   785     612 Ss+  bash .../install-root.sh
   1087      2 S+   apt-get install -y -qq unzip pipx python3-venv
   1092      2 S+   /usr/lib/apt/methods/http
   ```

   スクリプト開始から612秒たっていて、`apt-get install` は始まって2秒だった。つまり `apt-get update` だけで約10分かかっていた。

2. 最初の仮説は「IPv6 で接続しようとして待たされている」だった。名前解決の結果が IPv6 アドレスばかりだったため。

3. IPv4 と IPv6 を分けて計測し、仮説を確かめた。

   ```
   == IPv4 ==
   v4: 失敗か時間切れ
   == IPv6 ==
   curl: (7) Failed to connect to archive.ubuntu.com port 80 after 6 ms
   グローバルの IPv6 アドレスなし
   ```

   IPv6 は6ミリ秒ですぐ失敗していた（待たされていない）。時間切れになっていたのは IPv4 のほうだった。**仮説は外れていた。**

4. 宛先を変えて、どこまで届くかを切り分けた。

   ```
   http://archive.ubuntu.com/...       : 失敗か時間切れ
   https://archive.ubuntu.com/...      : 失敗か時間切れ
   http://security.ubuntu.com/...      : 失敗か時間切れ
   http://jp.archive.ubuntu.com/...    http=200 time=5.517566
   http://example.com/                 http=200 time=0.027229
   https://pypi.org/simple/checkov/    http=200 time=0.077425
   https://github.com/                 http=200 time=0.052137
   ```

   ほかのサイトは正常で、Ubuntu 公式の配布サーバーだけが応答していなかった。回線や WSL のネットワーク設定の問題ではないと判断した。

- **原因**: Ubuntu 公式の配布サーバー（`archive.ubuntu.com`、`security.ubuntu.com`）の一部が、この時間帯に応答していなかった。`apt` は応答しないサーバーを順に試すため、長い待ち時間になった。サーバー側で何が起きていたかは確認していない。

**対処**

1. 1回目の対処: 応答のあった公式の日本向けサーバー（`jp.archive.ubuntu.com`）に切り替えた。→ `apt-get update` が300秒の制限時間に達して失敗した（一部のファイルで取得のやり直しが起きていた）。

2. 取得速度を計測して比べた（約16MB のパッケージ一覧を取得）。

   | 取得元 | 結果 |
   |---|---|
   | `archive.ubuntu.com` | 20秒で1バイトも届かず |
   | `jp.archive.ubuntu.com` | 約 1.0 MB/秒（15.6秒） |
   | `ftp.udx.icscoe.jp`（国内ミラー） | 約 51.7 MB/秒（0.31秒） |
   | `ftp.riken.jp`（国内ミラー） | 約 45.2 MB/秒（0.35秒） |

3. 2回目の対処: 取得元を、その実行のときだけ理研のミラーに切り替えた。`/etc/apt` の設定は書き換えていない。

   ```bash
   KEYRING=/usr/share/keyrings/ubuntu-archive-keyring.gpg
   for suite in resolute resolute-updates resolute-security; do
     echo "deb [signed-by=${KEYRING}] https://ftp.riken.jp/Linux/ubuntu ${suite} main universe"
   done > "$TMP/mirror.list"

   apt-get -o "Dir::Etc::sourcelist=$TMP/mirror.list" -o "Dir::Etc::sourceparts=/dev/null" \
           -o Acquire::ForceIPv4=true -o Acquire::https::Timeout=20 -o Acquire::Retries=3 \
           -o Acquire::Languages=none update
   ```

   結果:

   ```
   Fetched 25.9 MB in 2s (13.6 MB/s)
   ```

- **ミラーを使ってよいと判断した理由**: パッケージは Ubuntu の鍵で署名されていて、`apt` が検証する。ミラー側で中身を差し替えることはできないので、取得元のサーバーが変わっても、入るものは同じ。

**学び**

- `-qq` で出力を消していたため、どこで止まっているかが見えなかった。時間のかかる処理は、進み具合が見える出力を残す。
- 制限時間（`timeout`）を付けていなかったため、止まっていることに気づくのが遅れた。外部に通信する処理には制限時間を付ける。
- 最初の仮説（IPv6）は、計測すると外れていた。思い込みで設定を変える前に、切り分けの計測をする。
- 「公式サーバーなら必ず届く」とは限らない。取得元を変数で切り替えられるようにしておく（保存したスクリプトでは `APT_MIRROR` で指定できる）。

### 5. 導入スクリプトが終了コード 141 で終わった

- **事象**: ツールはすべて入ったのに、スクリプトの終了コードが 141 で、最後の `gitleaks version` が実行されなかった。
- **原因**: スクリプトの先頭で `set -euo pipefail` を指定していた。最後の版表示で `tflint --version | head -1` を使っていて、`head` が1行読んで終了したあと、`tflint` 側が書き込み先を失って SIGPIPE（128 + 13 = 141）で終了した。`pipefail` がそれを失敗として扱った。
- **影響**: なし。別のコマンドで `gitleaks version` が `8.30.1` を返すことを確認した。
- **対処**: 保存版のスクリプト（`scripts/dev/install-tools-root.sh`）では、`head -1` の代わりに、入力を最後まで読む `sed -n 1p` を使っている。
- **学び**: `pipefail` を使うスクリプトでは、入力を途中で打ち切るコマンド（`head` など）をパイプの後ろに置かない。

### 6. checkov が3件失敗した（3件とも誤検知）

- **事象**:

  ```
  Passed checks: 130, Failed checks: 3, Skipped checks: 5

  Check: CKV_AWS_260: "Ensure no security groups allow ingress from 0.0.0.0:0 to port 80"
      FAILED for resource: module.network.aws_vpc_security_group_ingress_rule.web_http_from_monitor
  Check: CKV2_AWS_5: "Ensure that Security Groups are attached to another resource"
      FAILED for resource: module.network.aws_security_group.monitor
      FAILED for resource: module.network.aws_security_group.web
  ```

- **原因**:
  - `CKV_AWS_260`: このルールの送信元は、監視サーバーのセキュリティグループ（`referenced_security_group_id`）で、CIDR を指定していない。checkov はこれを「全世界に公開」と判定した。
  - `CKV2_AWS_5`: セキュリティグループは network モジュールで作り、EC2 への割り当ては compute モジュールで行っている。checkov はモジュールをまたいだ割り当てを追えなかった。
- **対処**: 該当するリソースにだけ、理由つきの除外コメント（`#checkov:skip=...`）を書いた。設定ファイルで全体から除外する方法は取らなかった（ほかのリソースで同じ指摘が本当に当たった場合に、見逃さないため）。
- **結果**:

  ```
  Passed checks: 130, Failed checks: 0, Skipped checks: 8
  ```

- **学び**: スキャンの指摘は、直す・理由を書いて除外する、のどちらかにする。除外はできるだけ狭い範囲（そのリソースだけ）にする。

### 7. `aws login --remote` で「まだプロジェクトはありません」と表示された

- **事象**: `aws login --remote` が表示した URL をブラウザーで開くと、認証コードの画面ではなく、次の画面になった。

  ```
  まだプロジェクトはありません
  事前設定済みの AWS 環境を使用して、より迅速に構築を開始できます。
  [初めてのプロジェクトを作成]  [セッションを追加]
  ```

- **調査**: AWS の公式ドキュメントで画面の意味を確認した。
  - この画面は「AWS sign-ins」（どのセッションで CLI を認証するかを選ぶ画面）。
  - 2026年に始まった「新しい AWS 体験」では、Google などのログインで AWS Builder ID を作り、その下に「プロジェクト」（中に AWS アカウントが1つ入る）を作る。
  - ブラウザーは AWS Builder ID でサインインしていたが、プロジェクトも、従来型の AWS アカウントのセッションもなかった。
  - 「初めてのプロジェクトを作成」は、新しい AWS アカウントを作る操作。「セッションを追加」は、すでにある AWS アカウント（ルートユーザーや IAM ユーザー）でサインインする操作。
- **新しい体験で作るアカウントの制約**（ドキュメントで確認）:
  - リージョンを選べない。連絡先の国で決まり、日本はシドニー（`ap-southeast-2`）になる。東京は選べない。
  - ルートユーザーがない。組織のポリシー（SCP）は AWS が管理する。
  - EC2・VPC・IAM・S3・Systems Manager・CloudWatch・SNS・Budgets は使える。
  - 有料プランでは、月額の上限（spend limit）を設定できる。
- **原因**: 最初の確認で「AWS アカウントはある」という回答をそのまま前提にし、アカウントの種類（従来型か、新しい体験か、Builder ID だけか）を確かめていなかった。
- **対処**: 新しいプロジェクトは作らずに止め、従来型のアカウントの有無を確認している。
- **続き（19:40）**: 「従来型のアカウントはある」という前提で「セッションを追加」に進んだが、サインインできなかった。
  - IAM ユーザーでのサインインには、12桁のアカウント ID かエイリアスが必要。どちらも分からなかった。
  - ルートユーザーとしてメールアドレスを入れると、次のエラーになった。

    ```
    エラーが発生しました
    指定されたサインイン情報の AWS アカウントは存在しません。
    もう一度お試しいただくか、または新しいアカウントを作成してください
    ```

  - このエラーは「パスワードが違う」ではなく「そのメールアドレスをルートユーザーとするアカウントがない」という意味。持っていたのは AWS Builder ID（個人のプロフィール）で、AWS アカウントそのものではなかった可能性が高い。別のメールアドレスで作ったアカウントがある可能性は残る。
- **続き（20:10）**: 受信箱で AWS からのメールを確認し、原因が分かった。
  - 2024年に従来型の AWS アカウントを作っていたが、同じ年に閉鎖していた。「AWS アカウント閉鎖の確認」と、その90日後の「AWS アカウント永久閉鎖の確認」（復元できない）のメールがあった。
  - つまり「アカウントを持っている」という記憶は正しかったが、そのアカウントはもう存在しなかった。サインイン画面の「アカウントは存在しません」は、この永久閉鎖によるもの。
  - AWS Builder ID のほうは別に作られていて、こちらは有効だった。
  - AWS のドキュメントによると、閉鎖したアカウントで使っていたメールアドレスは、別の AWS アカウントのルートユーザーのメールアドレスとして再利用できない。新しく作るには別のアドレス（Gmail の「+」付きアドレスなど）が必要になる。
  - **原因（確定）**: 従来型のアカウントは2024年に永久閉鎖済みだった。
- **続き（アカウントの作り直し）**: 従来型の登録 URL を開いたつもりが、`signup.aws.com/starter#/contactinformation`（連絡先情報の入力）という画面に進んでいた。
  - URL に `starter` とあること、右上に AWS Builder ID の名前が出ていること、名前の入力欄や利用規約の同意がなく連絡先だけを聞かれていることから、新しい方式（プロジェクトを作る登録）の画面と判断した。公式ドキュメントでも、新しい方式は連絡先の入力の次にプロジェクトが作られる。
  - ブラウザーが AWS Builder ID でサインインしたままだと、登録が新しい方式に進むと考えられる（推定）。
  - **対処**: 「続行」は押さずに止めた。Builder ID からサインアウトするか、シークレットウィンドウで従来型の登録 URL を開き直す。最初の画面で「ルートユーザーの E メールアドレス」と「AWS アカウント名」を聞かれれば、従来型の登録。
- **続き（検証コードが届かない）**: 従来型の登録画面には入れたが、検証コードの代わりに次のメールが届いた。

  ```
  指定されたメールアドレスは既に AWS アカウントに関連付けられています
  （中略）アカウントが完全に閉鎖されている場合、または新しいアカウントを作成することを
  ご希望の場合は、別のメールアドレスを入力する必要があります。
  ```

  - 閉鎖済みアカウントと同じメールアドレスを入力していたため。ドキュメントで確認していた制約（閉鎖したアカウントのメールアドレスは再利用できない）が、そのまま起きた。
  - 画面には「検証コードを送信しました」と表示されるが、実際に届くのはこの通知で、コードは届かない。画面の表示だけでは原因が分からない。
  - **対処**: メールアドレスを「+」付きの別アドレスに変えて、登録をやり直す。
  - **学び**: 手順を伝えるときは「別のアドレスで」ではなく、入力する文字列そのものを示す。
- **解決**: 「+」付きのアドレスで従来型のアカウントを作り直し、`aws login --remote` で認証できた。

  ```
  $ bash scripts/dev/aws-whoami.sh
  "Arn": "arn:aws:iam::<ACCOUNT_ID>:root"
  access_key : ****  : login
  region     : ap-northeast-1 : config-file
  "accountPlanType": "FREE", "accountPlanStatus": "ACTIVE",
  "accountPlanRemainingCredits": { "amount": 100.0, "unit": "USD" }
  ```

  - 以前アカウントを持っていたので対象外になると予想していたが、無料プランとクレジット 100 ドルが付いた。**この予想は外れた。**
  - Terraform の AWS プロバイダー（6.74）が `aws login` の認証情報をそのまま使えることも、`terraform plan` で確認した（`Plan: 7 to add`）。
  - 残った課題: ルートユーザーで認証している。日常の作業用に IAM ユーザーを作るかどうかを決める。
  - **学び（追加）**: AWS Builder ID と AWS アカウントは別のもの。Builder ID でサインインできても、AWS アカウントがあるとは限らない。「アカウントがある」の確認は、12桁のアカウント ID が分かるかどうかで行う。
- **学び**: 「アカウントがある」は、種類まで確認する。認証の画面で見慣れない選択肢が出たら、押す前に公式ドキュメントで意味を確認する（アカウントを作る操作は取り消しにくい）。

### 8. IAM ユーザーの確認画面で、管理者の権限が付いていなかった（作成前に気づいた）

- **事象**: IAM ユーザーの作成で、最後の「確認して作成」の画面の「許可の概要」に `IAMUserChangePassword` しか表示されていなかった。
- **原因**: 「許可を設定」の画面で、最初から選ばれている「ユーザーをグループに追加」のまま、グループを選ばずに「次へ」を押していた。この場合、エラーにはならず、権限なしのユーザーが作られる。`IAMUserChangePassword` は「次回サインイン時にパスワードを変更」にチェックを入れると自動で付くもので、作業用の権限ではない。
- **影響**: そのまま作成すると、サインインはできるが何も操作できないユーザーになり、`terraform plan` が権限エラーになるところだった。
- **対処**: 「前へ」で戻り、「ポリシーを直接アタッチする」を選んで `AdministratorAccess` を付ける。
- **学び**: 作成ボタンを押す前に、確認画面の「許可の概要」に意図した権限が並んでいるかを見る。

- **その後（IAM ユーザーでのサインインで起きたこと）**:
  - アカウント ID を1桁打ち間違えて「認証に失敗しました」になった。エラー文は「認証情報が無効であるか、有効になっていないリージョンにアクセスしようとしています」で、どの入力が違うのかは分からない。
  - 途中でやり直した結果、CLI 用の認証の流れがコンソール用の流れに入れ替わり、「400 Bad Request」になった。`aws login --remote` を実行し直し、新しい URL から始めて解決した。
  - 「AWS sign-ins」の画面では、押したカードのユーザーで認証される。root のカードを押すとルートユーザーのままになるので、`New sign-in` から IAM ユーザーを追加して、そのカードを押す。
- **解決**: `aws login` の認証が IAM ユーザーに切り替わった（`arn:aws:iam::<ACCOUNT_ID>:user/iac-admin`）。

### 9. state のロックの確認が、最初の方法では判定できなかった

- **事象**: ロックが効くことを確かめるために、`terraform plan` を2つ続けて実行し、2つ目が `Error acquiring the state lock` で止まることを期待した。結果は「止められなかった」だった。
- **原因**: 確認の方法の問題。1つ目の plan がロックを取っている時間は数秒しかなく、4秒待ってから始めた2つ目は、1つ目がロックを放したあとに動いていた。ロックが効いていないわけではなかった。
- **対処**: 確認の方法を変えた。`use_lockfile` が効いていれば、plan の実行中だけ S3 にロックファイル（`terraform.tfstate.tflock`）ができる。plan を裏で動かし、0.5秒おきにロックファイルの有無を調べる形にした。

  ```
  plan の結果: No changes. Your infrastructure matches the configuration.
  plan の実行中: ロックファイルあり（期待どおり）
  plan の終了後: ロックファイルなし（期待どおり）
  ```

- **学び**: 「タイミングが合えば失敗する」ことを期待する確認は、合わなかったときに何も分からない。仕組みが残す痕跡（ここではロックファイル）を直接見る確認にする。確認が「できなかった」ときに「問題なし」と報告しない。

### 10. Ansible が `aws login` の認証情報を使えなかった

- **事象**: 動的インベントリの読み込みが失敗した。

  ```
  Couldn't connect to AWS: Missing Dependency: Using the login credential provider
  requires an additional dependency. You will need to pip install "botocore[crt]" before proceeding.
  ```

- **原因**: `aws login` の認証情報を boto3（Ansible の AWS 用プラグインが使うライブラリ）から読むには、追加の依存（awscrt）が必要だった。AWS CLI や Terraform は自前で対応しているので、そちらでは起きなかった。
- **対処**: Ansible を入れた環境に awscrt を足した。最初は `pipx inject ansible-core "botocore[crt]"` を実行したが、botocore がすでに入っているため何も足されなかった。`pipx inject ansible-core awscrt` と、パッケージ名で指定し直して解決した。
- **学び**: 同じ認証情報でも、ツールごとに読める条件が違う。認証方式を変えたら、使うツールすべてで疎通を確かめる。

### 11. SSM Parameter Store に書き込むモジュールが、入れたコレクションになかった

- **事象**: 構文チェックで `couldn't resolve module/action 'amazon.aws.ssm_parameter'` になった。
- **原因**: `amazon.aws` コレクションにあるのは、読み取り用のプラグイン（lookup）だけだった。書き込み用のモジュールは別のコレクションにある。名前から「あるはず」と思い込んで書いていた。
- **対処**: コレクションを増やさず、AWS CLI を呼ぶ形にした（`aws ssm put-parameter --no-overwrite`）。先に読み取り用のプラグインで有無を調べ、ない場合だけ作る。
- **学び**: モジュール名は、入れたコレクションの中身で確かめてから書く。構文チェックを実行前に通す習慣が、ここで効いた。

### 12. SSM Parameter Store の読み取りが `AccessDenied` になった

- **事象**: playbook の1回目が、パスワードの有無を調べるところで止まった。

  ```
  Failed to access SSM parameter /aws-iac-monitoring/dev/zabbix/db-password (AccessDenied)
  ```

- **調査**: 管理者の権限を持つユーザーなのに拒否されたので、権限ではないと考えて CLI で同じ操作を試した。

  ```
  An error occurred (AccessDeniedException) when calling the GetParameter operation:
  No access to reserved parameter name: aws-iac-monitoring/dev/zabbix/db-password.
  ```

- **原因**: SSM Parameter Store では、`aws` や `ssm` で始まるパラメータ名を AWS が予約している。プロジェクト名をそのまま使った `/aws-iac-monitoring/...` がこれに当たっていた。
- **対処**: パラメータ名の先頭を `/iac-monitoring/dev` に変えた。
- **学び**: `AccessDenied` は、権限の不足とは限らない。Ansible のプラグイン経由だと詳しい理由が省かれるので、CLI で同じ操作をしてエラーの全文を見る。

### 13. 全検査をまとめて実行すると失敗になった

- **事象**: コミット前に `scripts/dev/check.sh` を実行すると、最後に「検査に失敗したものがあります」と出た。画面に見えていた各検査の結果は、どれも成功に見えた。
- **調査**: 検査を1つずつ実行して終了コードを見た。tflint だけが 1 を返していた。出力には `Missing version constraint for provider "null"` など、自分が書いていないコードへの警告が並んでいた。
- **原因**: tflint を `--recursive` でリポジトリ全体に対して実行していた。Ansible のコレクション（`ansible/collections/`）を入れたことで、その中に含まれる Terraform ファイルまで検査の対象になっていた。
- **対処**: tflint の対象を `terraform/` に絞った（`tflint --chdir=terraform --recursive`）。
- **学び**: 「全体を再帰的に検査する」設定は、あとから入れた外部のファイルを巻き込む。検査の対象は、自分のコードがある場所に明示して絞る。結果の要約だけを見て「通った」と判断せず、終了コードを見る。

### 14. Zabbix の API 用に足したインベントリが読み込まれなかった

- **事象**: Zabbix の設定用の playbook が、エラーなしで何もせずに終わった（`skipping: no hosts matched`）。終了コードは 0 だった。
- **原因**: `ansible.cfg` で、インベントリのプラグインを `amazon.aws.aws_ec2`（動的インベントリ）だけに限定していた。あとから足した、普通の YAML 形式のインベントリ（Zabbix の API の接続先）は、読める形式がなく無視されていた。
- **対処**: `enable_plugins` に `ansible.builtin.yaml` を足した。
- **学び**: 「対象が 0 台」は Ansible では成功として扱われる。終了コードが 0 でも、実行されたタスクの数を見る。

### 15. Zabbix のテンプレートの取り込みが、毎回「変更あり」になった

- **事象**: 設定用の playbook を2回続けて実行しても、テンプレートの取り込みが毎回 `changed` になった。
- **原因**: テンプレートを YAML で取り込むモジュールは、中身が同じかどうかを比べず、毎回取り込みを実行する。
- **対処**: ファイルの内容のハッシュ（SHA-256）を、テンプレートのタグ（`config_sha256`）に記録するようにした。実行のたびに Zabbix 側のタグとファイルのハッシュを比べ、違うときだけ取り込む。2回目の実行で `changed=0` になった。
- **学び**: 冪等でないモジュールは、「前回何を適用したか」を対象の側に記録して、自分で比べる。

### 16. CloudWatch の検知は、設計時の予想より早かった

- **事象**: CPU 負荷のテストで、CloudWatch のアラームが注入から約 118 秒で ALARM になった。設計の時点では「5 分間隔の値を使うので、Zabbix（128 秒）より遅い」と書いていた。
- **調査**: アラームの履歴とメトリクスの値を確認した。EC2 の基本モニタリングは 5 分に 1 回しか値を送らない。今回は、負荷をかけ始めてから約 2 分後に、たまたまその 1 回が来ていた。
- **結論**: 予想が間違っていたのではなく、言い方が不正確だった。CloudWatch の検知は、値が来るタイミングしだいで 1 分後にも 6 分後にもなる。今回は早い側に出た。「CloudWatch は遅い」ではなく「CloudWatch は検知までの時間が読めない」が正しい。
- **対処**: 設計の説明とテスト結果の文書（`docs/fault-injection.md`）に、1回の結果であることと、最悪の場合の時間を書いた。
- **学び**: 測った結果が予想と違ったら、予想に合わせて結果を解釈せず、なぜ違ったかを調べて書く。1回の測定で一般的な結論を出さない。

### 17. シェルをまたぐコマンドの引用符で、また止まった

- **事象**: 障害注入テストを続けて実行するコマンドが、`unexpected EOF while looking for matching` で始まる前に止まった。3番と同じ原因（PowerShell と bash の引用符の重なり）だった。
- **影響**: サーバーには何も注入されていなかった。出力を読んで、実行されていないことを確認してからやり直した。
- **対処**: 続けて実行する処理をスクリプト（`scripts/fault-injection/run-all.sh`）にした。
- **学び**: 3番で「インラインのコマンドを作り込まずにファイルにする」と書いたのに、同じことを繰り返した。記録するだけでなく、その場でスクリプトにする。

### 18. 通しの確認で、1回目の障害注入の記録が上書きされた

- **事象**: 環境を作り直して障害注入をもう一度実行したところ、`docs/evidence/` の記録3件が2回目の値で上書きされた。文書（`docs/fault-injection.md`）に書いた1回目の数値と、証跡のファイルの中身が食い違う状態になった。
- **原因**: テストの記録を、シナリオ名だけのファイル名（`nginx-stop.json` など）で保存していた。同じテストを繰り返すことを考えていなかった。
- **対処**: 2回目の記録を `docs/evidence/rebuild/` に移し、1回目の記録は Git から元に戻した。文書には、2回の結果を並べた表を足した。コミットする前に気づいたので、公開したリポジトリの内容は食い違っていない。
- **学び**: 文書に数値を書いたら、その元になった証跡が後から書き換わらないようにする。繰り返し実行するものは、実行ごとに別の場所へ保存する（スクリプトの直しは今後の課題）。
